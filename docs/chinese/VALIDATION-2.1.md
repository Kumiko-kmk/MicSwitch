# 2.1.0 验证记录

日期：2026-10-28。Windows 本机，3 个输入端点。EXE 49,664 bytes（48.5 KiB）。

## 延迟

通过 Windows 输入事件驱动真实全局 hook，由独立进程读取**全部三个系统输入端点**的静音状态。计时从注入按键开始，到全部端点符合目标状态为止，包含操作系统调度和测试轮询开销，不是单纯计时界面刷新。

|---|---:|---|---|
| 2.0.0 | 100 | 93.46 / 232.59 / 262.70 | 47.25 / 156.47 / 173.82 |
| 2.1.0 | 100 | 30.89 / 31.87 / 33.41 | 15.72 / 16.75 / 17.21 |
| 2.1.0，Edge 前台 | 20 | 30.82 / 32.11 / 32.53 | 15.83 / 16.63 / 16.67 |
| 2.1.0，微信前台 | 100 | 31.15 / 32.43 / 33.10 | 15.65 / 16.64 / 17.58 |

微信专项测试在每轮检查 `GetForegroundWindow`，确认始终是微信窗口；没有发送消息或发起通话。额外执行了 F8 自定义键盘热键的微信前台 100 轮测试，结果见 `verification-2.1/focus-keyboard.txt`。

## 持续运行与内存

连续 600 秒执行 566 轮开麦／松键循环。每 5 秒采样进程计数，**没有主动 GC 或清空工作集**。

- 私有内存：初始 74.156 MiB，结束 78.223 MiB。
- 第 3 分钟后：77.922–78.281 MiB，形成窄幅平台，没有持续线性增长。
- 句柄：818 → 808；线程：29 → 18。
- CPU：约 1.21% 单个逻辑核心，包含持续开关麦和三个端点的采集预热。

这支持“短时增加几 MB 是正常预热，没有在本次持续测试中发现泄漏”的结论，不是永不泄漏的证明。任务管理器的专用工作集与这里的 Private Bytes 是不同指标，不能直接比较。测试统计为主进程；独立保护进程另计。原始 CSV 位于 `verification-2.1/memory.csv`。

## 功能与实际声音

自动化测试通过：侧键 1/2、中键、F8、Ctrl+Alt+F9、现场录入 Ctrl+F8、错误修饰键、先松开修饰键、键盘连发不重新开麦、锁定/休眠防护状态、配置保存、设备离线及恢复、紧凑/展开界面。

另用独立 WASAPI 采集缓冲检查实际数据，未保存音频：

- 静音/松键后：两个端点峰值为零，另一个约 `2e-10`（−194 dBFS 的数值底噪）。
- 两个物理输入端点在开麦时读取到非零真实输入；虚拟输入无外部音源，保持零。
- 判定门限为 −80 dBFS，所有端点均通过。

首次检查误把 WAVE_FORMAT_EXTENSIBLE 的浮点采样作为整数读取；修正为无符号格式标签并解析子格式后，以上数值验证通过。测试程序保存在源码 `tests/CaptureTest.cs`。

开麦期间强制结束主程序，独立保护进程恢复全部输入端点静音，通过独立读取验证。每项测试结束均恢复测试前的系统静音状态。

## 优先级与边界

已读回进程优先级为 AboveNormal。热键由独立消息循环处理，控制线程接收事件后立即唤醒；音频初始化、采样与 UI 不在开麦控制路径中。

遵循微软关于[低级 hook 独立线程](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc)和[调度优先级](https://learn.microsoft.com/en-us/windows/win32/procthread/scheduling-priorities)的指导，不使用会妨碍系统输入线程的 RealTime 优先级。

验证覆盖本机普通权限的浏览器/微信前台，不代表实际网络通话的端到端延迟。没有发起双人通话，也未实测真实系统休眠、重新登录自动启动、管理员 UAC 流程、USB 拔插和独占驱动。代码提供相应通知处理及管理员重启入口；无法保证覆盖安全桌面、系统保留组合或所有第三方底层输入拦截。
